# Modern Data Platform on AWS

A production-inspired data engineering project that demonstrates modern cloud data platform practices using Infrastructure as Code, containerization, orchestration, analytics engineering, and CI/CD.

The project simulates an end-to-end telemetry data platform: synthetic truck telemetry is generated by a Python producer, landed in Amazon S3, ingested into Snowflake, transformed with dbt, and orchestrated with Apache Airflow.

The platform is designed with production-oriented engineering principles while keeping the scope appropriate for a portfolio project.

## Architecture

```text
Telemetry Generator
        │
        ▼
Python Producer
(Docker)
        │
        ▼
Amazon S3
(Raw Data Lake)
        │
        │ COPY INTO
        ▼
Snowflake RAW
        │
        │ dbt
        ▼
┌───────────────────┐
│    STAGING        │
│       ↓           │
│   INTERMEDIATE    │
│       ↓           │
│     MARTS         │
└───────┬───────────┘
        │
        ▼
Analytics-ready data


Apache Airflow
      │
      └── Orchestrates the pipeline
```

Airflow orchestrates the pipeline while the data flows through S3 and Snowflake.

## Data Flow

1. Python generates synthetic truck telemetry.
2. The Dockerized producer writes JSON files to S3.
3. Snowflake ingests new files from the external S3 stage using `COPY INTO`.
4. dbt transforms the raw JSON through STAGING, INTERMEDIATE, and MARTS layers.
5. Airflow orchestrates the producer, ingestion, and dbt steps.

## dbt Transformation Layer

The dbt project follows a layered transformation architecture:

RAW
  ↓
STAGING
  ↓
INTERMEDIATE
  ↓
MARTS

### Staging

Staging models extract and type fields from the raw JSON payload.
Example:
```text
stg_truck_telemetry
```
Responsibilities include:
* JSON field extraction
* Data type casting
* Basic data quality validation
* Standardized column naming

### Intermediate

Intermediate models contain reusable business-oriented transformations.
Example:
```text
int_telemetry_events
```
This layer derives analytical attributes such as movement state from telemetry status.

### Marts

Marts contain analytics-ready tables intended for downstream consumers.
Example:
```text
fct_telemetry_events
```
The fact mart contains the structured telemetry events together with derived attributes and ingestion metadata.

### Data Quality

The staging layer includes dbt tests for:

- Required telemetry identifiers
- Required event timestamps
- Accepted telemetry statuses
- Valid numeric ranges for telemetry measurements

The final dbt test suite passes successfully.

## Getting Started

### Prerequisites

* Python 3.12+
* Docker
* Terraform
* AWS CLI
* Git

Additional tooling is required for the local Airflow and dbt environments.

### Clone the Repository

```bash
git clone https://github.com/tahayasindemir/modern-data-platform.git
cd modern-data-platform
```

### Configure AWS Credentials

For local development, configure AWS credentials using the AWS CLI:

```bash
aws configure
```

GitHub Actions uses OIDC-based authentication rather than local AWS credentials.

### Provision Infrastructure

Initialize and review the Terraform configuration:

```bash
cd terraform
terraform init
terraform plan
terraform apply
```

`terraform plan` previews the infrastructure changes before they are applied. `terraform apply` creates or updates the resources defined in Terraform.

### Run the Telemetry Producer

```bash
cd producer
python main.py
```

The producer generates telemetry JSON files and uploads them to the configured S3 raw-data prefix.

### Run the Airflow Pipeline

The Airflow environment is defined under:

```text
airflow/
```

The DAG orchestrates:

```text
Telemetry Producer
        ↓
S3
        ↓
Snowflake RAW ingestion
        ↓
dbt transformations
        ↓
Snowflake MARTS
```

The Airflow environment uses Docker Compose for local orchestration.

### Run dbt Independently

The dbt project can also be executed independently from Airflow.

From the `dbt/` directory:

```bash
uv run dbt debug
uv run dbt run
uv run dbt test
```

The dbt project uses Snowflake as its target warehouse and separates transformation responsibilities into staging, intermediate, and mart layers.

## Snowflake Data Model

The Snowflake environment follows a layered structure:

```text
MDP
│
├── RAW
│   └── TRUCK_TELEMETRY
│
├── STAGING
│   └── STG_TRUCK_TELEMETRY
│
├── INTERMEDIATE
│   └── INT_TELEMETRY_EVENTS
│
└── MARTS
    └── FCT_TELEMETRY_EVENTS
```

Terraform manages Snowflake infrastructure and access configuration.

dbt manages analytical transformation models.

This separation keeps infrastructure provisioning and transformation logic independent.

## Design Decisions

### Batch Ingestion

The project uses Snowflake `COPY INTO` for batch ingestion from S3.

This was chosen intentionally because the project focuses on demonstrating the core data platform lifecycle without introducing unnecessary streaming infrastructure.

Snowpipe or event-driven ingestion could be introduced later if near-real-time processing became a requirement.

### Layered Data Modeling

The dbt project separates raw data, staging transformations, intermediate business logic, and analytical marts.

This provides clear ownership boundaries and makes transformations easier to test and maintain.

### Infrastructure as Code

AWS and Snowflake infrastructure are managed through Terraform rather than being configured manually wherever practical.

This provides:

* Reproducibility
* Version control
* Reviewable infrastructure changes
* Consistent environments

### Containerization

The telemetry producer and dbt workloads run in dedicated Docker containers.

Airflow orchestrates these workloads rather than embedding all application dependencies into a single Airflow image.

### Authentication

GitHub Actions authenticates to AWS using OIDC, avoiding long-lived AWS credentials stored in GitHub.

Snowflake authentication for local workloads uses key-pair authentication.
